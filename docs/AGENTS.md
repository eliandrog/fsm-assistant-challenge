# AGENTS.md

Instructions for any AI agent working in this repo. Read this file before doing anything.

## Rules (read first)

- **Never commit, stage, push, branch, or change git config/remotes unless the user explicitly says so.** A request to change code is not permission to commit; leave changes in the working tree for review.
- **`data/` is read-only.** Never modify `data/data.db` or `data/schema.sql`. Open the database read-only: `sqlite3 'file:data/data.db?mode=ro'`, or in Python `sqlite3.connect("file:data/data.db?mode=ro", uri=True)`.
- **Model-written SQL only ever runs on a read-only connection**, after validation in code (`sql_guard`). Never execute it on a writable connection, in tests or evals either.
- **Never commit or print secrets.** API keys go in `.env` (git-ignored); `.env.example` lists names only.
- **Scope priority: core functionality first.** In order: reliable natural language → SQL, rule proposal with backtesting, the evaluation suite. The interface stays deliberately minimal until those work.
- **Be honest in docs.** The README must describe only what exists. Mark anything unbuilt as "to be completed" or "proposed", and do not describe it in the present tense.
- **One task, one branch, one pull request.** Each task ships as its own branch and pull request, and its docs are updated in the same pull request: the decision entries it settles, the status it flips from Proposed to Built in `docs/ARCHITECTURE.md`, the current-state paragraph below and the README sections it affects. Only the user merges.
- **No dates about our work in docs** (no "as of", "last updated", dated decision entries). Dates that are facts about the data are fine.
- **Record decisions** in `docs/DECISIONS.md` (next D-number; never rewrite old entries), then update `docs/ARCHITECTURE.md` to match. Do not settle an item listed under "Open points" without the user.
- **No new dependencies without asking.** Six runtime dependencies are declared: `pydantic` (v2), for typed, immutable data models (D-19); `langchain-anthropic` (1.7), the Claude client; `langgraph` (1.2), for the turn graph (D-14, D-15, D-20); and `fastapi` with `uvicorn`, for the web chat's API (D-31). The dev tools are `pytest`, `mypy` and `httpx`, which the API's in-process test client needs. `langsmith` (0.16), which the Claude client and LangGraph bring in, is declared as well because `tracing.py` uses its client (D-27). Nothing else is added without asking: no `langchain` meta-package, no direct dependency on the `anthropic` SDK (it is installed because the wrapper needs it; the package does not import it), no `pydantic-settings`, no second provider. Only `llm.py` imports LangChain's Claude wrapper, only `llm.py` and `tracing.py` import LangSmith, only `api.py` imports FastAPI and only `cli.py` imports uvicorn. The web interface has its own dependencies in `frontend/package.json`; add none there without asking either.
- **No paid model call without the user's go-ahead for that run.** Tests never call a model, and run with network connections refused. Five commands call Claude. `fsm-assistant check-model` and `fsm-assistant eval` send nothing without `--yes-spend`; do not pass that flag unless the user has said to for that run. `fsm-assistant ask` and `fsm-assistant chat` call Claude as soon as they are run, with no flag to confirm: do not run them unless the user has said to for that run, or with `--replay-dir`, which sends nothing. `fsm-assistant serve` calls Claude for every question sent to it, and reads `.env`, so tracing may be on: run it only as `fsm-assistant serve --offline-demo`, which reads no `.env`, builds no client and no tracer and sends nothing, unless the user has said to run it live. `fsm-assistant graph`, `fsm-assistant scan`, `serve --offline-demo`, `check-model --replay`, `eval --list`, `eval --replay` and `eval --rescore` are free.
- **No test may reach LangSmith, and hosted tracing is off unless the user's settings enable it.** Tracing is on only when `LANGSMITH_TRACING=true` and `LANGSMITH_API_KEY` are in the user's settings (D-27); never set them, and never enable tracing in code, for a test or an experiment. A test of tracing hands the tracer `conftest.RecordingSink`, or gives `LangSmithSink` a fake HTTP session, and leaves no thread running. LangChain's and LangGraph's own tracing stays forced off around the model call and the whole graph run (`tracing.untraced`): it would send the turn state, rows included. A new field reaches a trace only by being added to `tracing.ALLOWED`, and nothing read from the database may be.
- **The web server is for local use only.** It listens on `127.0.0.1`, has no authentication and grants no cross-origin access (D-31). Do not add a CORS policy, bind it elsewhere by default, or serve it from a host that others can reach. It returns result rows to the browser that asked, which is the user's own screen, and writes them nowhere on the server: no response logging, no cache on disk, no request body in a log line. An API test uses the in-process test client and opens no port.
- **A log line holds no question, SQL, row, exception text or key.** Write it from counts, codes and class names (`applog.py`, D-27). Library code gets a logger with `logging.getLogger(__name__)` and never adds a handler; only `applog.configure`, called by a command, does.

## What this project is

A take-home submission for Checkout.com's "Fraud Success Manager Assistant Challenge" (full brief: `docs/CHALLENGE.md`). A Fraud Success Manager (FSM) explores transaction data, validates fraud hypotheses, and turns patterns into rules. The assistant should:

1. Translate natural-language questions into accurate SQL over the provided SQLite database (the brief's suggested MVP).
2. Help turn an insight into a **rule**: a valid SQL `WHERE` clause over the `transactions` table, backtested against `fraud_labels`.
3. Ship with an initial evaluation suite, and a README that justifies the design, covers GenAI limitations, and describes offline and online metrics.

Current state: a turn runs end to end in the terminal, and it has been tested with scripted model replies; against Claude, an earlier prompt (`turn-3`) has had one smoke test of `ask` (seven questions, run once each on `claude-haiku-5-5` and `claude-opus-5-5`, all answered correctly; `docs/ARCHITECTURE.md`, "Evidence"), which is not an evaluation. ## Conventions

- One responsibility per module, matching `docs/ARCHITECTURE.md`. Only `db.py` opens the database (every query goes through `db.run_query`); only `llm.py` talks to a model provider. Everything else uses `llm.IntentModel` and its plain request and reply types.
- In the turn graph, only `call_model` calls the model, only `guard_sql` writes `approved_sql` and only `execute_sql` runs it (the same for a rule clause), and only `remember` writes conversation memory. Rows live in state fields marked `UntrackedValue` and are never put in a prompt. **No text read from the database goes into a `Failure`, a repair, a trace line or any tracked field.** SQLite's message for a statement that failed while it ran can quote a row's value: use a fixed sentence there and put the message in `failure_detail`, which reaches the user only. Its message for text that did not compile may be passed on. **What the fraud scan finds is data too:** a segment's name and its counts may be shown to the user and are never remembered, put in a model message, sent in a trace or written to a log; the remembered scan turn holds the dimension titles, which are constants, and an event holds the number of segments listed and of statements run (D-27, D-29). Of the scan's SQL only the profile statement may leave the process: the statements after it name a segment as a literal. The scan's statements are written by code and still go through `sql_guard.check_query` and `db.run_query`. Text that code did not write goes into the prompt only through `prompt.tagged`. Anything model-written that is printed goes through `presentation.safe_text`. A field that belongs to one turn must be reset in `state.PER_TURN_RESET`, and a new type stored in tracked state must be added to `state.SAVED_TYPES`.
- A change to the prompt text (`prompt.py`) or to a tool description or schema (`nl2sql.py`) needs a new `nl2sql.PROMPT_VERSION`. A change to a tool description or schema also makes the committed `check-model` recordings stale: do not make one without the user. Either change, or a changed question in a case, makes a recorded evaluation run stale too; only a paid run renews it.
- Evaluation cases: a changed reference query needs `evals/expected.json` re-pinned (the snippet in `evals/README.md`; read the diff before keeping it), and a reference clause carries its four backtest counts in the case, with its month table and weakest month when the case is about the evidence by month. `tuned = true` marks a case whose question, or one nearly identical, is in the prompt or in `model_check.CHECK_QUESTIONS`, or for which a prompt line was written because it failed in a run; when the prompt gains such an example or such a line, re-mark the case and update the list in `tests/test_eval_cases.py`. A change made to the prompt, a scorer or a case because of a run's results is recorded as such in `evals/README.md` ("Results"), and the report of the run that prompted it is kept under `evals/results/history/`. Results are reported as counts per tier with tuned and held-out apart, never as one percentage, and no figure is claimed without a recorded run. A scorer change is followed by `eval --replay` (which lists the recorded cases that now score differently; say which and why) and, when the user agrees, `eval --rescore`; `run.json` is never edited by hand. A score's detail may quote a reference value and never a value of the turn's result.
- The web interface reads `TurnResult` and nothing else. Its types come from `types.gen.ts`; it never computes a figure, and it renders text that code did not write (the model's words, a database value) as text, never as HTML, through `lib/text.ts`. A new field of `TurnResult` is rendered in `frontend/src/components/` in the same change that adds it.
- `cli.py` is a thin entry point: argument parsing, wiring settings to the module that does the work, printing and exit codes (for `ask`: 0 answered, rule or clarification; 1 failed; 2 could not start; 3 could not answer; 4 rejected; 130 interrupted). A command's logic lives in its own module (`check-model` in `model_check.py`, `eval` in `evals/command.py`, which hands its lines to a callback), which returns values and text and never prints; `cli` imports that module, never the other way round.
- The API key is `Settings.anthropic_api_key`, a `SecretStr`. Only `llm.py` reads its value. The LangSmith key is `Settings.langsmith_api_key`, a `SecretStr` read only by `tracing.py`. Never put either in a message, a log line, an exception, a recording or a trace.
- Safety is enforced in code, not only in the prompt. Model-written SQL reaches `db` only after `sql_guard` accepted it: `db.inspect_query` has no timeout, and the guard's text limits are what bound a compile. A rule is measured only through `backtest` and `backtest_by_month`, each of which applies the rule policy itself.
- Numbers shown to the user (counts, fraud rates, precision, recall) come from executed SQL, never from model text.
- **Typed code, pydantic data (D-19).** `uv run mypy` must pass before a change is done, as `uv run pytest` must.
  - Every function and method has complete parameter and return annotations, in `tests/` as in `src/`: tests, fixtures and helpers included. No implicit `Any`; an explicit `Any` needs a one-line comment saying why (SQL bind parameters are the one case today).
  - Structured data is a frozen pydantic model (`model_config = ConfigDict(frozen=True, extra="forbid")`): settings, results, decisions, tool arguments, graph state, the turn result, and later evaluation cases and API bodies. No dataclass, `NamedTuple` or `TypedDict` for these.
  - A closed set of values is a `Literal` or an enum, not a bare `str`.
  - No untyped `dict` passed between modules. A dict is fine inside one function, for example on its way into `model_validate`. The one exception is a graph node's return value, which LangGraph takes as a dict: build it with `state.update(...)`, which checks the keys.
  - Exceptions stay ordinary exception classes with typed attributes.
  - Private working state that is updated in place and never leaves its module (`sql_guard._OpenCall`) may be a plain class.
  - No `# type: ignore` without an error code and a reason on the same line. In a test it is for a line that is ill-typed on purpose (assigning to a frozen field); an optional value is narrowed with `assert x is not None`, not ignored.
- Tests run offline. No test calls a real model: code that depends on one is tested with `llm.ScriptedModel`, and the live client by replacing the one method that performs the HTTP call. Anything that calls a real model belongs behind `eval --yes-spend` or `check-model --yes-spend`.
- Small, explainable changes. Say what changed and why.

## Data gotchas

Full detail in `docs/DATA.md`. The ones that cause wrong SQL:

- The brief's example rule uses `amount` and `'debit'`. The real column is `amount_usd_cents` (integer cents) and `card_type` is one of `'Credit'`, `'Debit'`, `'Debit (Prepaid)'` (case-sensitive).
- Two tables are not in the brief: `merchants` and `merchant_locations`. MCC is reached through `transactions.merchant_id → merchants.mcc`.
- `fraud_labels.transaction_id` is TEXT; `transactions.id` is INTEGER. Join with `f.transaction_id = CAST(t.id AS TEXT)`: the uncast form is correct but runs away (every transaction against every label) as a `LEFT JOIN` or `EXISTS` from `transactions`.
- `transactions.date` holds timestamps. End a day range with `< 'next day'`; `BETWEEN '2019-01-01' AND '2019-01-31'` drops the 31st.
- Join locations on `transactions.merchant_location_id = merchant_locations.id`, never on `merchant_id` (about 440 million rows).
- All 1,360 fraud labels are at merchant locations in Rome, Italy. Towns named Rome also exist in GA and NY, so read `city` with `state`.
- Only about 67% of transactions have a fraud label (777,339 of 1,159,966). An unlabelled transaction is unknown, not legitimate: compute fraud metrics with an inner join.
- Fraud is rare: 1,360 of the labelled transactions (about 0.17%).
- `amount_usd_cents` can be negative (56,900 rows).
- The database is in WAL mode; `data.db-shm` and `data.db-wal` are git-ignored sidecar files that a read-only connection creates on its first query, so the `data/` directory must be writable.
- A string in double quotes is a name, not text: `"amount" > 1000` is an error on the application's connection. A filter relative to today (`date('now')`) matches nothing, because the data ends on 2019-10-31; the guard rejects it.
